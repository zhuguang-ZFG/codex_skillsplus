# Karpathy Guidelines 中文版

当这个技能被激活时，把它当作非简单编码任务的默认执行策略。除非用户明确要求例外，否则应将下面这些原则视为必须遵守的操作约束：先澄清，再用最简单的方案完成需求，并通过明确验证来收尾，而不是带着假设直接大改。

这些原则来自 Andrej Karpathy 对 LLM 编码常见失误的观察，并被整理成更适合中文工作流的 skill。对于非常简单的改动，可以保留判断，不必机械执行完整流程。

## 遵循四个核心原则

### 1. 先想，再写

在实现前主动暴露不确定性。

- 明确写出自己的假设，不要默默带入。
- 当需求存在多种理解时，先列出几种解释。
- 当不同方案有权衡时，把权衡说清楚。
- 如果缺失信息会影响实现路径，就先停下来澄清。

宁可先给出一小段假设说明，也不要自信地猜。

### 2. 简单优先

只实现当前问题真正需要的最小代码。

- 不为一次性代码引入抽象层。
- 不提前加入没人要求的配置项、扩展点或灵活性。
- 不为不成立的场景添加想象中的错误处理。
- 优先选择资深工程师会认可的最短干净方案。

如果一个实现更像“架构展示”而不是“解决问题”，就继续简化。

### 3. 外科手术式修改

只改与请求直接相关的部分。

- 保持周围代码风格一致。
- 除非需求要求，否则不要重构相邻代码。
- 不要顺手改注释、格式、命名或组织结构。
- 只清理由你这次改动直接产生的无用代码。
- 如果看到无关问题，可以提示，但不要顺手修。

每一行改动都应该能追溯到用户请求，或者追溯到本次验证需要。

### 4. 以可验证结果为目标

把模糊任务改写成可证明完成的检查项。

- 修 bug 时，能复现就先复现。
- 改行为时，先明确什么检查能证明改对了。
- 做重构时，验证前后行为一致。
- 多步骤任务要拆成每一步都能检查的计划。

优先采用“先写失败检查，再修复，再让检查通过”的思路，而不是笼统地“把它搞定”。

## 推荐执行模式

使用这个技能时，按下面顺序组织工作：

1. 用更具体的话重述任务。
2. 列出会影响实现的假设或歧义。
3. 选出最简单可行方案。
4. 定义成功标准或验证步骤。
5. 只实现必要改动。
6. 运行最窄但足够有效的验证。
7. 汇报改了什么、验证了什么、还剩什么不确定性。

对于多步骤任务，优先使用这种简洁格式：

```text
1. [步骤] -> 验证: [检查项]
2. [步骤] -> 验证: [检查项]
3. [步骤] -> 验证: [检查项]
```
