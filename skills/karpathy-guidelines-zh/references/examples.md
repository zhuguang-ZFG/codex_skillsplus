# Karpathy Guidelines 中文案例

仅当当前任务需要具体例子时再读取本文件。

## 目录

- 先想，再写
- 简单优先
- 外科手术式修改
- 以可验证结果为目标

## 先想，再写

### 例子：隐藏假设

用户请求：

```text
给用户数据加一个导出功能。
```

不好的反应模式：

- 默认导出所有用户
- 默认导出为某种文件格式
- 默认导出到本地文件
- 默认某些字段都可以导出

更好的反应模式：

```text
实现前先确认：
1. 导出全部用户，还是导出筛选结果？
2. 是浏览器下载、API 返回，还是后台任务？
3. 哪些字段允许导出？
4. 数据量大概有多大？
```

### 例子：多种理解并存

用户请求：

```text
让搜索更快一点。
```

更好的反应模式：

```text
“更快”可能指更低延迟、更高吞吐，或者更好的体感速度。
下一步怎么做，取决于你更在意哪一种。
```

## 简单优先

### 例子：过度抽象

用户请求：

```text
加一个计算折扣的函数。
```

不好的反应模式：

- 直接建策略模式
- 提前支持多种折扣类型
- 提前引入配置对象

更好的反应模式：

```python
def calculate_discount(amount: float, percent: float) -> float:
    return amount * (percent / 100)
```

经验法则：

- 只有真实新需求出现时，才增加复杂度。

### 例子：提前加功能

用户请求：

```text
把用户偏好保存到数据库。
```

不好的反应模式：

- 顺手加缓存
- 顺手加通知
- 顺手加 merge 策略
- 顺手加配置开关

更好的反应模式：

- 直接把当前提供的偏好保存到数据库。

## 外科手术式修改

### 例子：顺手重构

用户请求：

```text
修复空邮箱导致校验器崩溃的问题。
```

不好的反应模式：

- 重写附近整段校验逻辑
- 顺手加强用户名校验
- 顺手改注释和格式

更好的反应模式：

- 只改邮箱为空时的处理逻辑
- 保持原有风格和无关行为不变

### 例子：风格漂移

用户请求：

```text
给上传函数加日志。
```

不好的反应模式：

- 顺手改引号风格
- 顺手补类型标注
- 顺手重写返回逻辑
- 顺手全局改异常处理写法

更好的反应模式：

- 加必要的 logger 定义
- 在现有成功和失败路径上插入日志
- 保持周围代码风格一致

## 以可验证结果为目标

### 例子：任务过于模糊

用户请求：

```text
把认证系统修好。
```

不好的反应模式：

- 看代码
- 做改进
- 测一下

更好的反应模式：

```text
先把具体问题定义清楚。
如果问题是“用户改密码后旧会话仍然有效”，那么：
1. 先写一个失败测试复现问题
2. 实现密码修改后会话失效
3. 验证新测试通过
4. 验证原有认证测试仍然通过
```

### 例子：多步骤改动

用户请求：

```text
给 API 加限流。
```

更好的反应模式：

```text
1. 先给单个接口加基础限流 -> 验证: 超过阈值返回 429
2. 提炼成中间件 -> 验证: 多个接口都受控
3. 如果需要多实例共享，再接入共享存储 -> 验证: 计数跨实例一致
```

## 总结性判断准则

- 如果你在猜，就停下来把猜测说出来。
- 如果你在抽象，就先问自己这个需求今天是否真的存在。
- 如果你在改周边代码，就先问自己这是不是当前请求必需的一部分。
- 如果你没法证明任务完成，就先定义更好的检查方式。
